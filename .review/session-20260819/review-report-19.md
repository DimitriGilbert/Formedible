### [SEVERITY: HIGH] Finding 1: `form-options-analytics-contract.ts` is entirely dead — zero consumers, zero enforcement
**File**: tests/compatibility-examples/form-options-analytics-contract.ts:[13-71]
**Problem**: None of the file's three exports (`formOptionsAnalyticsContract`, `restoredFormOptionsAnalytics`, `intentionallyRemovedFormOptionsAnalytics`) is imported by any test, package, or script. The file is only type-checked by `tsc -p tests/compatibility-examples/tsconfig.json` inside `pnpm check-types` (root package.json:20) — compilation is not enforcement.
**Evidence**: Repo-wide grep for all three export names matches only the defining file itself (3 hits, all in this file). `tests/formedible/phase10-behavior.test.ts` and `validation/validation-pipeline.test.tsx` import only from `use-formedible-return-contract`; `compatibility-matrix.test.ts` reads `docs/formedible-compatibility-matrix.md`, not this file; no doc or script reads the file as text either.
**Impact**: The file presents itself as the authoritative disposition contract for ~49 options/callbacks/return-helpers ("restored" / "removed-replace" / "superseded"), but any row can drift from the implementation with no test ever failing. The `restored` claims are in fact accurate today (spot-checked `formOptions.onChange/onBlur/onFocus/onReset` wiring at `packages/formedible/src/hooks/use-formedible.tsx:409,415,425,589`), but that accuracy is coincidental and unguarded — exactly the "vacuous contract" failure mode this suite exists to prevent.
**Suggestion**: Consume it: e.g. a test asserting every `restored` row's option exists on `UseFormedibleOptions`/`FormedibleFormOptions`/`FormedibleAnalyticsConfig` types (compile-level via tsconfig.types.json) and that the `restored` analytics callbacks fire (extend the existing tracker tests); or delete the file so it stops pretending to be a gate.

### [SEVERITY: HIGH] Finding 2: `example-manifest.ts` wiring is never executed; `arrayFields` and `advancedFieldTypes` fixtures are dead
**File**: tests/compatibility-examples/example-manifest.ts:[75-92]; tests/compatibility-examples/nested-examples.ts:[8-69]; tests/compatibility-examples/core-examples.ts:[251-317]
**Problem**: `compatibilityExamplesManifest` and `compatibilityExampleIds` have no importers. The only import of `example-manifest` outside the fixture directory is `import type { FieldDescriptor }` in `tests/formedible/basic-fields.test.tsx:25` — type-only, erased at runtime. Consequently the two fixtures reachable ONLY through the manifest — `arrayFieldsCompatibilityExample` (nested-examples.ts:8) and `advancedFieldTypesCompatibilityExample` (core-examples.ts:251) — are never loaded by any test runner. Their `assertionsRequired` (e.g. "teamMembers requires at least one item and allows at most ten", "contactMethods requires at least one valid email item", "location search results are expected to map to id, lat, lng, address, city, state, country, postalCode, and relevance fields") are unenforced prose.
**Evidence**: Repo-wide grep: `arrayFieldsCompatibilityExample` and `advancedFieldTypesCompatibilityExample` appear only in their defining files and the manifest (lines 10/18/84/89). `compatibilityExamplesManifest`/`compatibilityExampleIds` appear only at example-manifest.ts:75,92. Docs (`docs/formedible-test-expansion-plan.md:242-247`) say "Use the compatibility manifest/tests as the coverage checklist" naming exactly these fixtures — the plan's checklist is not actually wired. Partial indirect coverage exists elsewhere (consumer-smoke has its own verbatim copy `tests/consumer-smoke/fixtures/old-array-fields-app.tsx`; the advanced example lives as a component in apps/web), but neither consumes these fixtures, so fixture drift/regression is invisible.
**Impact**: 2 of the 14 canonical examples have dead compat fixtures. Notably, the advanced fixture's location-result assertion (`id`, `postalCode`, `relevance` fields) currently holds only through `FormedibleLocationValue`'s `[customProp: string]: unknown` escape hatch (`types.ts:618-626` names only lat/lng/address/city/state/country) — the silent-shrinkage case these fixtures were built to catch, and nothing would notice. Manifest integrity itself (14 entries, unique ids) is also unchecked at runtime.
**Suggestion**: Add a manifest-consuming test (e.g. `compatibilityExampleIds` deepEquals the 14 expected ids; each id maps to a non-empty `assertionsRequired`), and either route the nested/advanced test runners through these fixtures (as basic-fields/phase10 do for theirs) or delete the two dead fixtures so the "executable compatibility surface" claim stays honest.

### [SEVERITY: MEDIUM] Finding 3: Contract dispositions mislabel regressions — main-fired callbacks marked 'superseded', `onSubmitInvalid` described as a "debug helper"
**File**: tests/compatibility-examples/form-options-analytics-contract.ts:[41,45,51,58]
**Problem**: Beyond being unenforced (Finding 1), the disposition/reason text is dishonest about compat history. `analytics.onTabChange` (line 41), `analytics.onTabFirstVisit` (line 45), and `analytics.onSubmissionPerformance` (line 51) are marked `superseded` with "No current package runtime event truthfully emits…" — but these were actually fired by the original implementation (`main:packages/formedible/src/hooks/use-formedible.tsx:834,888,712`; audit F5). By the file's own taxonomy (`removed-replace` = removed old behavior), these are removals of working main behavior reclassified as benign supersession. Similarly `formOptions.onSubmitInvalid` (line 58) gets reason "Removed debug/validation helper" — it was never a debug helper; it is a standard TanStack submit callback that main forwarded (`main:use-formedible.tsx:668-669`). `resetOnSubmitSuccess`/`autoScroll` (lines 52-53) reuse a generic "Superseded by … TanStack Form validation state" reason that is factually wrong for reset/scroll behavior.
**Impact**: If this file is ever wired into a gate or read as documentation (its stated purpose), a future maintainer would conclude no working behavior was lost in these rows. This is distinct from the KNOWN coverage gap: the file doesn't omit these options, it actively misclassifies them.
**Suggestion**: Split the taxonomy (e.g. add `removed-breaking` or mark these rows `removed-replace` with reasons that state main fired them), or annotate each with the main-branch call-site evidence.

### [SEVERITY: MEDIUM] Finding 4: Return contract's "keep" side is never verified against the actual hook — only the removals are enforced
**File**: tests/compatibility-examples/use-formedible-return-contract.ts:[34-36]
**Problem**: `keptUseFormedibleReturnFields` is consumed exactly once, in `tests/formedible/phase10-behavior.test.ts:198-213`, where it is deepEqual'd against a hand-copied literal array — that pins the fixture's text to the test's text, but verifies nothing about `useFormedible` itself. `validation/validation-pipeline.test.tsx:258-281` does verify the real hook, but only that the 4 REMOVED keys are absent. No runtime or type-level test asserts the hook return CONTAINS the 14 keep keys, and no `.test-d.ts` ties `ReturnType<typeof useFormedible>` to the contract.
**Evidence**: Grep for keep keys (`progressValue`, `visiblePages`, `goToPreviousPage`, `isFirstPage`) across `tests/formedible/**` matches only the phase10 literal list. Hook return today is exactly the 14 keys (`packages/formedible/src/hooks/use-formedible.tsx:664-679`), so the contract is currently accurate — the gap is enforcement asymmetry, not active drift.
**Impact**: If the rewrite ever drops a keep key (e.g. `progressValue` or `visiblePages` in a refactor), no contract fixture or test fails; the phase10 test would keep passing because both sides of its deepEqual live in test code.
**Suggestion**: In the existing `ContractProbe` (validation-pipeline.test.tsx:259-272), add `for (const kept of keptUseFormedibleReturnFields) assert.equal(Object.hasOwn(formedible, kept), true);` — one line makes the fixture the enforced source of truth for both sides.

### [SEVERITY: MEDIUM] Finding 5: `vacationFlow` fixture is only decoratively consumed — its data is hand-copied in the test and the fixture itself gets two self-referential assertions
**File**: tests/compatibility-examples/advanced-field-examples.ts:[6-52]
**Problem**: The sole consumer (`tests/formedible/advanced-fields.test.tsx`) never renders or evaluates the fixture's fields/pages. It defines its own `vacationFlowFields`/`vacationFlowPages` (lines 173-192) by hand and tests THOSE, using a local regex-based `interpolateDynamicText` (lines 194-196) instead of the package's `resolveDynamicText`, and a hand-written `conditional` closure instead of the package's conditional evaluation. The fixture itself is touched only at lines 233-234: `assert.ok(vacationFlowCompatibilityExample.fields.some((field) => field.type === 'date'))` and `'multiSelect'` — assertions about the fixture's own data that can only fail if someone edits the fixture, i.e. permanently vacuous.
**Evidence**: advanced-fields.test.tsx:20 (import), 173-196 (hand-copied data + local interpolation), 233-242 (only fixture usage + tests against the hand-copied copies). The real `resolveDynamicText` IS properly tested, but in phase10-behavior.test.ts:182 with its own template — not via this fixture.
**Impact**: `advanced-field-examples.ts` contributes no executable coverage of the rewrite; the flow-form example's `assertionsRequired` (token interpolation, carType visibility, passengers min) are enforced against test-local clones. The fixture can drift arbitrarily from what is tested without any failure, which defeats its purpose as the compatibility source of truth.
**Suggestion**: Derive `vacationFlowFields`/`vacationFlowPages` from the fixture (mapping descriptors to configs as basic-fields/phase10 do), or assert the fixture deepEquals the hand-written copies so drift is caught; use `resolveDynamicText` instead of the local regex.
