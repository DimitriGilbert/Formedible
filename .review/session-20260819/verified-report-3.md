### Finding 1: Duration picker text input destroyed by parse/format round-trip — CONFIRMED
**Original**: Free-text input value is `formatDurationText(parseDuration(field.value))` recomputed every render while `onChange` commits every keystroke; intermediate text without a unit suffix parses to `{0,0,0}` and is rewritten to `'0'`, so typing is impossible.
**Verification**: Code confirmed at `duration-picker-field.tsx:19` (`parts = parseDuration(field.value)`), `:37-44` (`value={formatDurationText(parts, format)}`, `onChange={(event) => update(parseDurationText(...))}`). There is no local draft state. Empirical simulation of the exact state machine (format `'hms'`): initial render `"0"`; user types `"1"` → commits `{0,0,0,totalSeconds:0}` → re-rendered input `"0"` (digit destroyed); typing `"h"` next yields target `"0h"` → parses to `{0,0,0}` → `"0"` again. Only complete unit-bearing strings (`"1h"`, `"1h 30m 45s"`) survive a single change event — i.e. only paste-style entry works, exactly as reported. Each keystroke also runs the full `onChange` pipeline (analytics, `formOptions.onChange`, `scheduleAutoSubmit`) with the collapsed value, per `use-formedible.tsx:417-427`.

### Finding 2: Duration picker unit mismatch for `hours`/`minutes` formats — CONFIRMED
**Original**: `formatDurationOutput` emits hours/minutes for those formats, but `parseDuration` treats any number as total seconds; selects snap back after each interaction and follow-up edits corrupt the stored value.
**Verification**: Code confirmed: `parseDuration` (line 80-81) routes all numbers to `parseTotalSeconds`; `formatDurationOutput` (127-133) returns `parts.hours + parts.minutes/60 + ...` for `'hours'` and minutes for `'minutes'`. `'hours'`/`'minutes'` are declared public config values (`types.ts:610`). Empirical trace, format `'hours'`: select Hours=2 → stores `2` → next render `parseDuration(2)` → `{hours:0, minutes:0, seconds:2}` → Hours select shows `00`, text shows `"2s"` (snap-back confirmed). Then setting Seconds=30 (the stray select, Finding 3) → stores `0.008333` hours instead of the intended `2.008333`. Format `'minutes'`: select Minutes=30 → stores `30` → re-parsed `{0,0,30}` → Minutes select snaps to `00`, text `"30s"`. Only `'seconds'` (round-trips as total seconds) and the object formats are consistent. Minor note: the report's illustrative "then sets Minutes=30" step cannot occur via a Minutes *select* under `format:'hours'` (no such select renders — see Finding 3); the corruption path runs through the stray Seconds select or the text input, and the arithmetic defect and snap-back are real regardless.

### Finding 5: Date field converts Date values/bounds via `toISOString()` (UTC), shifting a day east of UTC — CONFIRMED
**Original**: `toDateInputValue`/`toDateBound` use `toISOString().slice(0,10)` (UTC), so local-midnight Dates east of UTC render as the previous day; min/max bounds shift too. Distinct from the known date-submits-string issue.
**Verification**: Code confirmed at `date-field.tsx:5-19`, used at `:31-33` (`value`, `min`, `max`). Empirical under `TZ=Europe/Berlin`: `new Date(2026, 0, 15)` (local midnight) → `toISOString().slice(0,10)` = `'2026-01-14'`; `minDate = new Date(2030, 0, 1)` → bound `'2029-12-31'`. The public API explicitly allows `Date` (`minDate?: Date | string`, `types.ts:520-521`), and Date-typed defaults/programmatic values flow through `toDateInputValue`, so the path is reachable. This is the Date→display/bounds conversion path — genuinely distinct from the known/intentional-tracked "submits string" finding, which is about the `onChange` path; not a duplicate.

### Finding 6: Date field calls `disableDate` with an Invalid Date when cleared/mid-edit — CONFIRMED
**Original**: On clear/edit the handler builds `new Date(`${nextValue}T00:00:00`)` → Invalid Date, and passes it to the user-supplied `disableDate` with no guard.
**Verification**: Code confirmed at `date-field.tsx:40-48`: `new Date('T00:00:00').getTime()` → `NaN` (Invalid Date, verified empirically), and `dateConfig?.disableDate?.(nextDate, ...)` is invoked unconditionally — the optional chaining only guards a missing callback, not an invalid date. The callback contract is `(date: Date, values) => boolean` (`types.ts:522`), so consumer implementations calling `date.toISOString()` throw `RangeError: Invalid time value` inside the React event handler, and implementations returning truthy for NaN make the field unclearable. One phrasing caveat: an exception thrown in a React event handler is an uncaught error that aborts the handler — it does not unmount the form tree, so "crashes the form" is slightly overstated; the unguarded Invalid Date reaching user code (and blocking the clear path when the callback throws or returns truthy) is real. Confirmed with that severity framing note.

### Finding 7: Multi-select nests remove `<button>`s inside the trigger `<button>` — CONFIRMED
**Original**: Badge remove actions are real `<button>`s inside the trigger `<button>` — invalid HTML, hydration failures for SSR consumers, a11y problems.
**Verification**: `Button` renders a genuine `<button>` element (`packages/formedible/src/components/ui/button.tsx`, `ComponentProps<'button'>`). Structure at `multi-select-field.tsx:65-100`: trigger `Button` → `<span>` → `Badge` (a `<span>`, `badge.tsx`) → remove `Button` (:82-94) — an actual `<button>` descendant of a `<button>`. HTML's content model forbids interactive content inside a button, and the HTML parsing algorithm closes the open `<button>` when a nested one starts, so browser-parsed SSR HTML structurally differs from React's vdom → hydration mismatch for any SSR consumer of this published package (the current docs app is Vite CSR, which is why it doesn't surface there — matches the report's own caveat). Confirmed as a real library defect, not a framework convention.

### Finding 8: Autocomplete input never syncs with external field value changes — CONFIRMED
**Original**: `inputValue` is local state initialized once from `field.value`; no effect re-syncs, so resets/programmatic sets leave stale text; with `allowCustom: false` blur neither commits nor reverts.
**Verification**: `autocomplete-field.tsx:74` initializes once; the only `useEffect` (103-152) handles async option loading — no `field.value → setInputValue` sync anywhere in the file. The `form.Field` wrapper is keyed by field name (`use-formedible.tsx:395`, `key={options?.key ?? fieldName}`), so external value changes re-render but never remount, and the input keeps stale text while the form holds the new value. Secondary gap confirmed at `:170-176`: `onBlur` commits only when `shouldCommitCustomAutocompleteValue(allowCustom)` (default true), and with `allowCustom: false` the typed text is neither committed nor reverted to the selected option's label. Other fields in the cluster derive display from `field.value` each render, so this is an inconsistency, not a codebase-wide convention. Confirmed.
