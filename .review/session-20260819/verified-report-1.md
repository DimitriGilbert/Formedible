# Verified Report 1 — Core form engine (use-formedible.tsx et al.)

Verification method: read every referenced owning source under `packages/formedible/src/`, cross-checked all TanStack claims against the installed `@tanstack/form-core@1.32.0` / `@tanstack+react-form@1.32.0` sources in `node_modules/.pnpm`, and ran two empirical jsdom+React 19.2.5 tests in `/tmp` scratch (deleted after) rendering the real `useForm` hook. No repo files were modified.

## Verified TanStack runtime facts (all three hold)

1. **`useForm` does not subscribe the host.** `react-form/dist/esm/useForm.js` contains no `useStore` on the host — only `extendedApi.Subscribe` (a `LocalSubscribe` wrapper over `useStore`) and `Field` subscribe. `form.state` is a getter (`get state() { return formApi.store.state; }`) so event-handler reads are live but render-time reads are frozen until an unrelated host re-render. **Empirically confirmed**: rendering a host with `useForm` + `form.Field`, calling `field.handleChange('typed')` produced 1 host render before and 1 after — no host re-render on value change.
2. **Field unmount resets field meta.** `form-core/dist/esm/FieldApi.js` (mount cleanup, ~line 88): `fieldMetaBase[this.name] = { ...defaultFieldMeta, isTouched, isBlurred, isDirty }` — errors wiped, only interaction flags preserved.
3. **`_handleSubmit` semantics** (`FormApi.js` lines 454-568): marks all field instances `isTouched`, bails to `onSubmitInvalid` when `!state.canSubmit`, sets `isSubmitting: true` in the store, runs `validateAllFields('submit')` then form `validate('submit')`, calling `onSubmitInvalid` with populated `fieldMeta` on failure; the catch block does `done(); throw err;` — re-throws errors raised by `options.onSubmit`. `isSubmitting` is store state (`defaultState.isSubmitting ?? false`, line 13).

### Finding 1: Conditional pages/tabs never react to value changes — CONFIRMED
**Original**: `visiblePages`/`visibleTabs`/`totalPages`/`progressValue` are computed from `form.state.values` captured at hook-host render time; since TanStack v1 `useForm` never re-renders the host on value changes, conditional pages only update on unrelated re-renders (tab click, nav, submit attempt).
**Verification**: Real. `use-formedible.tsx:160-166` passes `values: form.state.values` to `useMultiPage`/`useFormTabs`; the host has zero store subscriptions (verified in `useForm.js`, and empirically — no host re-render on `handleChange`). `use-multi-page.ts:63` keys the `visiblePages` `useMemo` on that render-time `values` object; `goToNextPage`/`goToPreviousPage` (lines 88-102) close over `safeVisiblePages` from that render. `use-form-tabs.ts:32-35` likewise. The bounce trace in the report is accurate: click Next → `changePage(staleNextPage)` passes the stale `safeVisiblePages.includes(toPage)` guard → `setCurrentPage(2)` → host re-render recomputes visible pages → the effect at `use-multi-page.ts:71-75` resets to page 1. Note the contrast inside the same file: conditional *fields* work because `renderFields(formValues)` runs inside `form.Subscribe` (line 608-614), but `FormProgress`/`FormTabs` props (`multiPage.visiblePages/totalPages/progressValue`, `tabs.visibleTabs`) all come from the stale host scope (lines 536-547, 621-627). The shipped example `apps/web/src/components/docs/examples/conditional-pages-form.tsx` matches the described scenario exactly (pages 2/3 gated on `values.applicationType`, page 5 on `values.needsPremium`; the example component holds no local state, so nothing external re-renders the host). "conditional pages" is required behavior (FROM-SCRATCH-2.md line 214).

### Finding 2: Persistence autosave never triggers while the user types — CONFIRMED
**Original**: `useFormPersistence` computes `persistedValuesSignature` only during host render, so its debounced-save effect never re-runs from typing; saves only happen on page/tab navigation or submit attempts.
**Verification**: Real. `use-form-persistence.ts:100-102` sets `latestValuesRef.current` and derives `persistedValuesSignature` during render; the save effect (lines 155-167) depends on `[config, persistedValuesSignature, saveToStorage]`. Since value changes never re-render the host (empirically confirmed, see Finding 1), typing changes neither the signature nor `saveToStorage`'s identity (`useCallback` deps `[config, currentPage]`, line 113) — no save is scheduled. One minor over-claim in the report: on tab-only forms a tab click does *not* re-run the effect either (nothing in the deps changes), so the actual triggers are page navigation, submit attempts (via `setHasInvalidSubmitAttempt`), and consumer-driven re-renders — the core claim ("typing schedules no save") is fully correct. The shipped `persistence-form.tsx` example uses `debounceMs: 1500` with no manual save call, and "persistence" is a required behavior (FROM-SCRATCH-2.md line 216).

### Finding 3: `Form` is redefined on every hook render — remounts the form and clears TanStack field errors — CONFIRMED
**Original**: `function Form(...)` inside `useFormedible` yields a new component type per host render; React remounts the subtree; `FieldApi` unmount cleanup wipes recorded errors, so inline errors visible while typing disappear on the first submit attempt / navigation.
**Verification**: Real, and **empirically reproduced** with the installed `@tanstack/react-form@1.32.0` under React 19.2.5 + jsdom: a `FormLike` component recreated inside the host (mirroring `use-formedible.tsx:552`) wrapping `form.Field` with an `onSubmit` validator — after an invalid `handleSubmit()`, `fieldMeta.name.errors` was `["required"]`; after one host re-render (the identity change), it was `[]`. The wipe mechanism is the `fieldMetaBase` reset in `FieldApi.js` mount cleanup (verified, runtime fact 2). Guaranteed re-render triggers exist on normal flows: `setHasInvalidSubmitAttempt(true)` at lines 599 and 89, `multiPage.setCurrentPage` on nav, `tabs.setActiveTab` on tab click. Fallout claims check out: `field.state.meta.errors` at line 395 feeds `error`, which drives `FieldError`/`data-invalid` in `field-wrapper.tsx:35,47`; `isTouched` survives the reset so remounted fields do not re-validate (no onMount validators are built in `validation.ts`), leaving errors blank until the user edits again. FROM-SCRATCH-2.md line 352 requires "All validation errors render in the normal field error area".

### Finding 4: Submit handler early-returns before `form.handleSubmit()` — submit-path errors never persisted to field meta — CONFIRMED
**Original**: The DOM `onSubmit` runs a manual `getInvalidFieldEntries` check and returns before calling `form.handleSubmit()`, so TanStack's submit lifecycle (mark touched, `validateAllFields('submit')`, populate `fieldMeta`) never runs for the common invalid case.
**Verification**: Real. `use-formedible.tsx:593-604` shows exactly the quoted early return. `_handleSubmit`'s touched-marking and `validateAllFields('submit')` (FormApi.js lines 465-487) therefore never execute on this path; on pristine fields `fieldMeta` has no errors, so inline `FieldError`/`aria-invalid` never appear — only the summary (which recomputes entries by re-running validators inside `Subscribe`, line 611/618) shows anything. `onSubmitInvalid` (lines 88-91) is effectively dead for sync field validation because the manual check re-runs the identical combined validator chain (`getFieldErrorFromConfiguredValidation` → `buildFieldValidators(...).onSubmit`, validation.ts lines 327-342 — onChange/onBlur/onSubmit bodies are identical). Not an intentional design: the author wired `onSubmitInvalid` expecting the TanStack lifecycle to run, and the report's suggested fix (always `handleSubmit()`, navigate in `onSubmitInvalid`) matches the existing structure. Combined with Finding 3, inline errors are absent after submit in both paths.

### Finding 5: `getValuesWithFieldUpdate` corrupts values for nested field paths — CONFIRMED (mechanism detail corrected)
**Original**: `{ ...form.state.values, [fieldName]: nextValue }` with dotted/bracketed names gives the consumer's `onChange` a values object with a bogus literal key and a stale nested object.
**Verification**: Real, with one detail corrected. `use-formedible.tsx:134-136` and the call at 424-425 are as quoted, and nested fields genuinely route through this closure: `fields/object-field.tsx:30-36` renders subfields as `renderField(nestedConfig, { name: joinFieldPath(field.name, nestedConfig.name) })` and `fields/array-field.tsx:106,139,149-153` uses `arrayItemFieldPath`/`joinFieldPath` (e.g. `contacts[0].email`). **Empirically verified** against the real form: after `field.handleChange('new@x')` on `contacts[0].email`, the store held the fresh nested value (handleChange commits synchronously — the report's "stale nested object / values.contacts[0].email still holds the pre-change value" detail is wrong), but `getValuesWithFieldUpdate` delivered `{ contacts: [...], 'contacts[0].email': 'new@x' }` — a bogus literal top-level key. So the delivered `value` and `formApi.state.values` in `FormedibleFormOptions.onChange` (types.ts:364, a documented public callback) are still shape-corrupted: `Object.keys(value)` includes the bogus path key, and any serialization/iteration of the delivered object carries garbage. Nested paths are required behavior (FROM-SCRATCH-2.md "Nested Field Requirements"). Confirmed, with lower severity than the original wording implies (polluted shape, not wrong values).

### Finding 6: `isSubmitting` is read non-reactively — controls never disable during an async submit — CONFIRMED
**Original**: `Form` reads `form.state.isSubmitting` during host render; with no host subscription the guard never activates, and a double click during an async submit reaches `onSubmitInvalid` spuriously.
**Verification**: Real. `use-formedible.tsx:553-554` is as quoted; `isSubmitting` is store state (FormApi.js line 13, set true/false inside `_handleSubmit`), and nothing subscribes the host or `Form` to it — the `fieldset disabled` (line 607) and both submit buttons (lines 647-651) are created in `Form`'s render scope, outside `form.Subscribe` (whose selector `values`/`fieldMeta` doesn't include `isSubmitting` anyway). Empirically the host does not re-render on store updates (Finding 1 test). The double-submit claim also checks out against FormApi.js lines 475-478: while `isSubmitting` is true, `canSubmit` is false, so the second `_handleSubmit` immediately calls `onSubmitInvalid` → `setHasInvalidSubmitAttempt(true)` → spurious invalid-state UI plus the Finding 3 remount. Only `config.disabled`/`config.loading` (prop-driven re-renders) can ever disable controls.

### Finding 7: Invalid-entry computation runs on every store update and re-parses the whole schema per field — CONFIRMED
**Original**: `getInvalidFieldEntries` runs unconditionally inside `form.Subscribe` on every values/fieldMeta change; for each field without a meta error the built `onSubmit` validator re-runs `schemaFieldMessage`, which parses the entire form values with the schema.
**Verification**: Real. `use-formedible.tsx:608-613` calls `getInvalidFieldEntries({ values: formValues, fieldMeta: state.fieldMeta })` unconditionally on every Subscribe render (every keystroke). At line 256, fields without a meta error fall through (`??`) to `getFieldErrorFromConfiguredValidation`, which invokes the built `onSubmit` (lines 234-246); its `schemaFieldMessage` (validation.ts:238-250) calls `formApi.parseValuesWithSchema(schema)` per field, and `FormApi.parseValuesWithSchema` (FormApi.js:859) runs `standardSchemaValidators.validate({ value: this.state.values, ... })` — a full-values parse with no caching, once per field per render. The only consumers of the counts gate on `validationSummaryConfig.showBadges && hasInvalidSubmitAttempt` (lines 547, 625), so the work is wasted whenever that conjunction is false. O(fields × full-schema-parse) per keystroke for schema-backed forms is accurate.

### Finding 8: Abandon analytics report a completion percentage frozen at the last host render — CONFIRMED
**Original**: `abandonContextRef.current = getAbandonContext()` stores an eagerly computed snapshot, so `onFormAbandon` under-reports completion for values typed since the last host re-render.
**Verification**: Real. `use-formedible.tsx:213-214` shows the contrast exactly as quoted: `pageValidationStateRef.current = getPageValidationState` (function, reads live `form.state` when invoked) vs `abandonContextRef.current = getAbandonContext()` (result, frozen at host render). `useFormAnalytics`'s unmount cleanup (use-form-analytics.ts:69-87) reads `optionsRef.current.getAbandonContext?.()` which returns the frozen object. Since value changes never re-render the host (empirically confirmed), anything typed since the last page/tab switch or submit attempt is missing from `completionPercentage`. The one-line fix (store the function, as done one line above for `pageValidationStateRef`) is valid.

### Finding 9: `form.handleSubmit()` rejections are unhandled; `clearStorage()` is skipped when the consumer's `onSubmit` throws — CONFIRMED
**Original**: `handleSubmit()` is a floating promise in three places; form-core re-throws `onSubmit` errors, so a failing consumer `onSubmit` becomes an unhandled rejection and skips `clearStorage()`.
**Verification**: Real. The three call sites are `use-formedible.tsx:130` (`getFormApiContext().handleSubmit`), `:152` (`scheduleAutoSubmit` timeout), and `:604` (DOM submit) — none attaches `.catch`. FormApi.js's catch block (lines 557-569) does `done(); throw err;`, verified. The hook's own `onSubmit` (lines 92-96) awaits the consumer callback before `clearStorage()`, so a rejection skips the clear; `analytics.trackFormComplete(value)` fires *before* the consumer's `onSubmit` runs, so failed submits are reported complete. All three impact claims verified against source.

### Finding 10: Duplicate section headers when a section title is a ReactNode — CONFIRMED
**Original**: `getSectionKey` returns `undefined` for non-string titles, so the dedup condition renders one header per field for ReactNode-titled sections.
**Verification**: Real. `use-formedible.tsx:363` returns `undefined` when `section.title` is not a string; line 463's `shouldRenderHeader = !previousFieldHadSection || sectionKey === undefined || ...` is then always true via the `sectionKey === undefined` clause, and line 465-467 pushes a header for every field in that section (keyed `${fieldConfig.name}-section`, so React renders both). `FormedibleFieldSection.title` is typed `ReactNode` (types.ts:60) and `resolveDynamicText` passes non-strings through untouched (dynamic-text.ts:7-9), so a `title: <span>Premium</span>` config reaches this path unchanged. String-titled sections group correctly via the `sectionKey !== previousSectionKey` clause, confirming the inconsistency. Verified end to end in code.

### Finding 11: `onReset` fires callbacks and analytics without resetting form values — CONFIRMED
**Original**: The reset handler never calls `form.reset()`, so a consumer-supplied `<button type="reset">` fires reset callbacks/analytics while the TanStack store keeps old values.
**Verification**: Real. `use-formedible.tsx:587-592` matches the quoted code: `onReset` invokes the consumer's `onReset`, `config.formOptions.onReset`, `config.onFormReset`, and `analytics.trackFormReset('reset')` — no `form.reset()` anywhere (grep over `packages/formedible/src` finds zero `.reset()` calls). Values live in the TanStack store which a native DOM reset does not touch. Severity LOW is appropriate: no built-in component renders a reset button (grep for `type="reset"` in the package returns nothing), so this only bites consumers who add their own.

## Verdict summary

All 11 findings confirmed as real. Two wording corrections noted inline, neither of which dismisses a finding:
- Finding 5: the nested value is *fresh* (handleChange commits synchronously — empirically shown); the corruption is the bogus literal top-level key (`'contacts[0].email'`) delivered to `formOptions.onChange`, not a stale nested object.
- Finding 2: on tab-only forms, tab clicks don't trigger saves either (effect deps don't include `activeTab`) — the set of working triggers is even narrower than reported.

False-positive signals checked and rejected: no store subscription exists anywhere in the host path (useForm source + empirical); the custom `formedibleValidationLogic` does not mitigate Findings 3/4 (it runs onChange+Blur validators on change, but the unmount wipe clears those errors too, and onSubmit validators never populate meta on the early-return path); `parseValuesWithSchema` exists on FormApi (so Finding 7's per-field parse path executes rather than crashing); no `form.reset()` elsewhere compensates for Finding 11; the "no issues" file assessments (form.tsx, field-renderer.tsx, types.ts, normalize-field-config.ts, field-path.ts) and the SSR note were spot-checked and not contradicted.
