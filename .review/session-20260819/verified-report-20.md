### Finding 2: writeFile detection evades on concatenation, parens in literals, and comma-bearing first arguments — CONFIRMED

**Original**: `findWriteFileMutationViolations` only flags an argument that starts with a quote/backtick or equals a tracked variable; the argument extractor is not string-literal aware; the forbidden writeFile regexes use `[^,]+,` for the first argument.

**Verification** (verbatim replay of tests/architecture/copy-only-sync-contract.test.ts:6-84 logic in /tmp):
- Tracked-variable concat (`const header = <template literal starting with export...>; writeFile(target, header + source)`) → **EVADES**: extracted arg is `header + source`; `isGeneratedContentExpression` is false (startsWith quote check fails) and `generatedVariables.has('header + source')` is false because the set membership requires exact equality of the whole argument.
- Literal as second operand (`writeFile(target, source + <backtick literal starting with export...>)`) → **EVADES**: arg starts with the identifier `source`, and no forbidden pattern matches (the `writeFile\s*\([^,]+,\s*(?:`|['"])(?:export|import)\b` regex requires the literal immediately after the comma).
- Paren inside a string literal (`writeFile(target, source + ')export const a = 1;')`) → **EVADES**: the character scanner decrements depth on the `)` inside the literal, slicing the argument to the fragment `source + '`, which fails both checks.
- Comma in the first argument (`writeFile(join(root, name), '// generated by hand')`) → both forbidden writeFile regexes return false (`[^,]+` cannot span the comma inside `join(root, name)`); only the mutation extractor catches this case, and per the previous bullet the extractor is itself unreliable — exactly as the report states.
- Control: the suite's own sample (literal-first concat) is caught, confirming the scan is calibrated only to the literal-first shape and the four evasions are real gaps beyond it.
